## [SIGCHAIN-1] Pending payment signatures do not bind the mutable payout and fee configuration
**Severity**: High
**Category**: evm-audit-signatures / evm-audit-chain-specific
**Location**: `NavyPayments.payInvoice()`
**Description**: Circle's EIP-3009 authorization correctly binds `payer`, `address(NavyPayments)`, `amount`, the validity window, and the invoice-derived nonce, but it only authorizes a transfer into NavyPayments. It does not bind the merchant payout address, treasury, or `feeBps` used for the subsequent split. All three values can change after the payer signs and before an allowlisted relayer submits. A compromised or operationally mistaken owner can therefore redirect an already authorized invoice's merchant portion and increase its fee (up to 10%) without invalidating the payer's signature. This is a privileged-but-plausible trigger that causes direct loss of the payment principal to its intended recipient; the immutable EIP-712 verifying contract does not protect mutable downstream routing.
**Proof of Concept**: (1) Merchant `M` is active with payout `P`, treasury `T`, and a 1% fee. A payer signs `ReceiveWithAuthorization(from=payer,to=NavyPayments,value=100e6,nonce=keccak256(M,invoice),...)`. (2) Before relay, the owner calls `setMerchantPayout(M, attacker)` and `setConfig(1000, attacker)`. (3) An allowlisted relayer submits the unchanged signed fields. Circle validates the signature because neither `P`, `T`, nor the fee appears in the EIP-3009 struct or nonce. (4) NavyPayments sends 90 USDC to the attacker payout and 10 USDC to the attacker treasury, then irrevocably marks the invoice paid. The payer's signature remains cryptographically valid although none of the intended split recipients or economics is preserved.
**Recommendation**: Bind a configuration snapshot into the authorization nonce, for example `keccak256(abi.encode(merchantId, invoiceId, expectedPayout, expectedTreasury, expectedFeeBps))`, while keeping a separate stable invoice key for `invoicePaid`. Accept the expected values as calldata, require them to equal current configuration, and redeem only the derived nonce. A configuration change will then invalidate pending authorizations and require an explicit re-sign. Include all security-relevant routing/economic fields in backend typed-data generation and receipt reconciliation tests.

## [SIGCHAIN-2] Merkle execution plans are reusable across vault deployments and chains
**Severity**: Medium
**Category**: evm-audit-signatures / evm-audit-chain-specific
**Location**: `NavyVaultSRCLA.submitPlan()` / `NavyVaultSRCLA.executeNextActionWithProof()`
**Description**: The Merkle action leaf contains only `planId`, index, kind, adapter, amount, and `minOut`; it does not contain `block.chainid`, the vault address, or the vault asset. `submitPlan` stores only a subset of `PlanHeader` and ignores `configurationDigest`, `snapshotBlockNumber`, `snapshotHash`, `policyVersion`, and the risk commitments. Although adapters expose a digest containing `block.chainid`, the vault never validates it. Consequently the same header, root, and proofs are valid on another NavyVault deployment (including another chain) whenever the same allocator key is authorized and the referenced numeric adapter addresses are registered. This defeats the apparent configuration/snapshot commitment and turns a wrong-RPC or cross-deployment replay into executable asset movement. The trigger is allocator/operator compromise or misrouting, so impact is Medium rather than an unprivileged replay.
**Proof of Concept**: Deploy vaults `V1` and `V2`, grant the same allocator on both, and register adapters at the same numeric address (readily achievable with deterministic deployments) with sufficient idle assets. Construct one plan whose leaf is `keccak256(abi.encode(planId,index,kind,adapter,amount,minOut))`. Submit the identical `PlanHeader` and root to both vaults; neither call checks a chain/vault domain or the supplied `configurationDigest`. The identical proof passes in both `executeNextActionWithProof` calls and moves funds twice under a plan that could have been generated for only `V1`. Changing the ignored header digest or snapshot fields does not affect acceptance.
**Recommendation**: Define a canonical plan domain containing at least `block.chainid`, `address(this)`, `asset()`, policy version, and a digest of the registered adapters plus caps/configuration. Commit that domain in the Merkle root/leaf (or an EIP-712 plan authorization) and recompute and validate it on submission and execution. Reject stale snapshot/configuration fields instead of accepting and ignoring them. Add a test proving a plan generated for one vault or chain fails on another.

## Historical coverage / no-findings (2026-08-12 baseline)

- Read the complete requested signature and chain-specific checklists and traced the current production Solidity for raw/EIP-712 signatures, EIP-3009, replay state, nonces, expiry, caller binding, contract wallets, L2 time/block assumptions, chain identity, oracle/sequencer behavior, gas accounting, native-value sends, opcodes, and precompiles.
- Circle EIP-3009 correctly domain-separates the authorization by the USDC proxy address and dynamic `block.chainid`; the signed struct binds payer, NavyPayments as recipient, amount, `validAfter`, `validBefore`, and nonce. Circle rejects high-`s`/invalid signatures, marks authorization state per authorizer and nonce, and `receiveWithAuthorization` requires `msg.sender == to`. Thus cross-token/cross-chain replay, replay from another payer, malformed-signature recovery, direct mempool theft, and submission by a third-party payee were not found. A second allowlisted relayer can race the first only to execute the exact same bound payment; transaction atomicity rolls back both Circle nonce state and `invoicePaid` if any later split transfer reverts.
- Validity uses Circle's strict timestamp bounds. Base/OP sequencer ordering can delay inclusion or cause an authorization to expire, but cannot alter its amount, payer, recipient, nonce, or downstream result. Relayer availability/censorship until expiry is an explicit trusted-liveness assumption, not a fund-theft path. No contract logic assumes a fixed block interval or uses `block.number` as elapsed time.
- Circle's current implementation supports ERC-1271 through its arbitrary-`bytes` overload. Navy exposes only the legacy `v,r,s` overload, so it can pass only a 65-byte signature. Contract wallets whose ERC-1271 validator accepts that representation can work; wallets requiring arbitrary-length signatures cannot, and EIP-7702 accounts are treated as contracts and must validate through ERC-1271. The repository explicitly declares plain-EOA payers as an accepted product constraint, so this is recorded as a compatibility assumption rather than a security finding. If contract-wallet payers enter scope, add the `bytes signature` overload end to end and test representative ERC-1271 and EIP-7702 implementations.
- No first-party production code performs raw `ecrecover`, handwritten EIP-712 hashing, `abi.encodePacked` hashing of adjacent dynamic fields, ERC-2612/DAI permit submission, ERC-2771 forwarding, arbitrary meta-transaction execution, signature-based role changes, or user-supplied gas forwarding. `keccak256(abi.encodePacked(bytes16,bytes16))` is unambiguous because both invoice components are fixed width.
- The Base deployment/asset-identity gap is already fully reported as GENERAL-5: the only vault script is Sepolia-oriented and neither script nor constructor enforces chain 8453 or canonical Base USDC. The absence of a Base sequencer-uptime check and recovery grace period is already fully reported as AMMORACLE-7. They are not duplicated here; SIGCHAIN-2 covers the distinct failure to domain-separate executable plans after deployment.
- No source uses `tx.origin`, `block.prevrandao`, `block.difficulty`, chain-specific precompiles, hardcoded call gas, `transfer`/`send` native ETH, or on-chain L1/L2 gas-cost profitability calculations. Solc 0.8.24 targets Cancun, which is compatible with the declared Base/Sepolia environments. Adapter configuration digests use dynamic `block.chainid`, but their non-enforcement is addressed in SIGCHAIN-2.
- Reward swap deadlines, oracle freshness, plan expiry, and daily buckets use `block.timestamp`. Their Base sequencing assumptions do not create an additional standalone exploit beyond the already reported oracle recovery gap; allocator-only execution and short router deadlines constrain ordinary public-mempool front-running but do not repair the separate slippage/oracle defects reported by the AMM/oracle specialist.
