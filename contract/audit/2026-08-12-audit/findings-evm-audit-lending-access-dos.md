## [LENDACCESS-1] MoonwellAdapter uses nonexistent mToken selectors, omits approvals, and misinterprets protocol accounting
**Severity**: High
**Category**: evm-audit-defi-lending / evm-audit-access-control / evm-audit-dos
**Location**: `MoonwellAdapter.deposit()` and `MoonwellAdapter.withdraw()`
**Description**: Base Moonwell's official `MErc20Delegator` exposes `mint(uint256) returns (uint256 errorCode)` and `redeemUnderlying(uint256) returns (uint256 errorCode)`. The adapter instead calls `mint(address,uint256)` and `redeemUnderlying(address,uint256)`, selectors the mUSDC deployment does not expose. Its deposit flow also attempts a second `safeTransferFrom(vault, adapter, amount)` even though `NavyVaultSRCLA._deploy()` already transferred the assets, and it never approves mUSDC to pull the adapter's USDC. Even after correcting the selectors, the returned Compound-style error code must be checked for zero rather than merely wrapped in `try/catch`. Finally, `totalAssets()` divides `mTokenBalance * exchangeRateStored()` by `1e8`; Moonwell's own ERC-4626 wrapper divides by `1e18`, so the current valuation would overstate a USDC position by 10^10. This adapter cannot deposit or withdraw against the configured Base market and would catastrophically misaccount a position if tokens were transferred into it directly.
**Proof of Concept**: Official selectors are `mint(uint256) = 0xa0712d68` and `redeemUnderlying(uint256) = 0x852a12e3`; the adapter sends `0x40c10f19` and `0x96294178`. Calling `deposit()` from the vault first reverts at `safeTransferFrom` because the vault did not approve the adapter; if that is bypassed, the nonexistent mint selector reverts. Calling `withdraw()` reaches a nonexistent selector and reverts. Separately, an mToken balance of `50e8` at exchange rate `2e16` represents `100e6` USDC (`50e8 * 2e16 / 1e18`), but the adapter reports `1e18` base units (`/ 1e8`). RPC-gated fork tests did not run in this audit environment and return early when `BASE_RPC_URL` is absent, which is why these incompatibilities are not caught locally.
**Recommendation**: Use Moonwell's official `MErc20` interface. The adapter should consume the USDC already transferred by the vault, approve the mToken, call `uint256 code = mUsdc.mint(amount)`, and revert unless `code == 0`. Withdrawal should call `redeemUnderlying(amount)`, verify code zero, then transfer the received USDC to the immutable vault. Divide exchange-rate products by `1e18`. Query pause state through the Unitroller/Comptroller proxy, not `mUsdc.mintGuardianPaused()`, and add a mandatory live-Base vault-to-adapter fork test.

## [LENDACCESS-2] RewardExecutor route administration is permanently assigned to a contract that cannot exercise it
**Severity**: High
**Category**: evm-audit-defi-lending / evm-audit-access-control / evm-audit-dos
**Location**: `RewardExecutor.constructor()`
**Description**: The constructor grants both `DEFAULT_ADMIN_ROLE` and `ADMIN_ROLE` exclusively to `_vault`. In production `_vault` is `NavyVaultSRCLA`, but that contract has no function that calls `approveRoute`, `revokeRoute`, `setDailyVolume`, `grantRole`, or arbitrary executor calldata. Ethereum callers cannot impersonate a contract address, so no route can ever be approved and no executor role can ever be reassigned. Every nonzero reward swap therefore permanently reverts with `RouteNotFound`. Unit tests hide the deadlock by setting `vault` to an EOA and using `vm.prank(vault)`.
**Proof of Concept**: (1) Deploy `NavyVaultSRCLA`. (2) Deploy `RewardExecutor(address(vault), router)`. (3) An admin EOA calls `approveRoute` and fails `onlyRole(ADMIN_ROLE)`. (4) The vault address owns the role, but the vault exposes no forwarding/configuration entry point, so it cannot make the call. (5) Since the vault is also the only default admin, nobody can grant the role to an operator. Any later `harvest` with a positive reward amount reaches `swap` with an unapproved route and reverts forever.
**Recommendation**: Pass a distinct governance/admin address to the constructor and grant it `DEFAULT_ADMIN_ROLE`/`ADMIN_ROLE`, while retaining the vault only as the authorized swap caller. Prefer `AccessControlDefaultAdminRules` with a delayed two-step admin transfer. Alternatively add narrowly scoped, admin-gated route-management forwarding functions to the vault and test them with the vault as an actual contract, not a prankable EOA.

## [LENDACCESS-3] Plan headers and adapter configuration digests are decorative and can be bypassed entirely
**Severity**: Medium
**Category**: evm-audit-defi-lending / evm-audit-access-control / evm-audit-dos
**Location**: `NavyVaultSRCLA.submitPlan()`
**Description**: `VaultTypes.PlanHeader` includes `policyVersion`, `createdAt`, snapshot block/hash, `configurationDigest`, reserve, `minFinalAssets`, `maxRecognizedLoss`, and `turnoverLimit`, but `submitPlan()` ignores all of them. It stores only plan ID, decision hash, expiry, action count, and the separately supplied root. Although every adapter exposes `configurationDigest()`, the vault's private adapter interface omits it and no execution path compares the current protocol configuration with the plan. The parallel `executePlan()` entry point bypasses Merkle roots and all header fields completely. An allocator can therefore execute a plan generated for stale addresses, risk policy, snapshots, or loss/turnover limits while on-chain observability misleadingly records a decision hash.
**Proof of Concept**: Construct a header with `configurationDigest = bytes32(0)`, `policyVersion = 0`, a future `snapshotBlockNumber`, `minFinalAssets = type(uint256).max`, `maxRecognizedLoss = 0`, and `turnoverLimit = 0`; pair it with a Merkle root containing an otherwise executable Deploy action. `submitPlan` accepts it and `executeNextActionWithProof` executes the action without checking any of those contradictory constraints. Alternatively call `executePlan()` with the same action and no Merkle/header data at all.
**Recommendation**: Choose one plan mechanism. Compute a canonical live configuration digest from chain ID, asset, active adapters and each adapter's digest/limits; require it to equal the header. Validate snapshot freshness/hash, policy version, plan-level loss, final-assets, reserve, and turnover constraints during submission and/or completion. Remove or strictly gate the uncommitted `executePlan()` path so it cannot bypass the committed-policy path.

## [LENDACCESS-4] Aave and failed adapter reads overstate immediately withdrawable liquidity
**Severity**: Medium
**Category**: evm-audit-defi-lending / evm-audit-access-control / evm-audit-dos
**Location**: `AaveV3Adapter.maxWithdrawable()` and `NavyVaultSRCLA.synchronousLiquidity()`
**Description**: Aave's adapter reports its entire aUSDC balance as immediately withdrawable without bounding it by reserve cash. At high utilization Aave withdrawals can revert even though the aToken balance remains unchanged. The vault compounds this error: when any adapter's `maxWithdrawable()` reverts (pause, deprecation, upgrade, or malformed adapter), its catch branch adds the full cached `strategyAssets` instead of zero. `maxWithdraw`/`maxRedeem` thus advertise liquidity precisely when the protocol cannot establish it, causing user transactions and plan divests to revert. The adapter `try/catch` wrappers only replace revert data with `WithdrawFailed`; they provide no fallback liquidity and are not protocol-pause resilience.
**Proof of Concept**: (1) Let the Aave reserve's available USDC fall below the adapter's aUSDC balance, or use a registered adapter whose `maxWithdrawable()` reverts. (2) `synchronousLiquidity()` includes the full cached position. (3) `maxWithdraw(user)` returns a value backed by that fictitious synchronous liquidity. (4) An allocator attempting to divest the quoted amount reaches Aave `withdraw`, which reverts for insufficient reserve cash; a user withdrawal also cannot receive the advertised assets. The same false-positive fallback is deterministic for any reverting adapter read.
**Recommendation**: Aave `maxWithdrawable` should return the minimum of the adapter position and current underlying reserve liquidity (using the correct aToken/Pool accounting). In `synchronousLiquidity`, treat a failed read as zero and emit/monitor adapter health outside the view path. Do not describe a catch-and-revert wrapper as resilience; provide withdrawal ordering, partial pulls, and an explicit impaired-state fallback.

## [LENDACCESS-5] First-party lending rewards cannot be claimed and will never enter the harvest pipeline
**Severity**: Medium
**Category**: evm-audit-defi-lending / evm-audit-access-control / evm-audit-dos
**Location**: `NavyVaultSRCLA._harvestCore()`
**Description**: All three lending adapters advertise reward tokens but hard-code `claimableReward()` to zero and implement no claim method. The vault merely reads `claimableReward`; it never invokes a protocol rewards controller or `IRewardSource.claimReward`. If a future adapter reports a positive amount, the vault approves the executor to pull that amount from the vault even though protocol rewards are held by/claimable to the adapter, so the executor transfer also fails unless rewards were separately moved. Compound COMP, Moonwell WELL, and any Aave incentives therefore remain unclaimed and are excluded from user value despite the production-facing harvest API and events.
**Proof of Concept**: Deposit through any first-party adapter and allow protocol incentives to accrue. `rewardTokens()` returns `[COMP]` or `[WELL]`, but `claimableReward(supportedToken)` always returns zero. Calling `harvest` completes with `totalUsdcReceived == 0`, does not call a rewards contract, and leaves accrued rewards untouched. There is no other source function that claims or transfers them to the vault.
**Recommendation**: Implement protocol-specific claiming using the official Aave incentives controller, Compound CometRewards, and Moonwell MultiRewardDistributor/Comptroller. Use a canonical adapter method such as `claimReward(token, maxAmount) returns (claimed)` that transfers the measured claimed balance to the vault, then swap the actual balance delta. Do not advertise unsupported reward tokens; disable harvesting until a fork test proves claim-to-swap-to-USDC end to end.

## [LENDACCESS-6] A compromised default admin can grant itself allocator power and drain vault assets through a lying adapter
**Severity**: Medium
**Category**: evm-audit-defi-lending / evm-audit-access-control / evm-audit-dos
**Location**: `NavyVaultSRCLA.constructor()`
**Description**: The deployer receives both unrestricted `DEFAULT_ADMIN_ROLE` and `ADMIN_ROLE`, with no delay, multisig enforcement, or two-step transfer. That key can grant itself `ALLOCATOR_ROLE`, set `minIdleBps` to zero, register an arbitrary adapter that merely returns the expected `vault()` and `asset()` values, and execute a Deploy action. `_deploy` transfers USDC to the adapter before trusting its reported credit, so a malicious adapter can keep all assets and return any value. The interface probes are not a custody guarantee. This is an explicit owner-key rug path and contradicts meaningful admin/allocator separation.
**Proof of Concept**: After compromising the deployer/default-admin key: (1) deploy EvilAdapter whose `vault()` and `asset()` report the expected values and whose `deposit(uint256)` returns `amount` while retaining received USDC; (2) grant the attacker `ALLOCATOR_ROLE`; (3) set `minIdleBps(0)` and register EvilAdapter with `capBps = 10_000`; (4) execute a Deploy action for all vault idle assets. The safe transfer succeeds, EvilAdapter lies about credit, and the attacker controls the received USDC. No timelock gives users an exit window.
**Recommendation**: Put `DEFAULT_ADMIN_ROLE` behind a production multisig plus timelock and use delayed two-step default-admin transfer. Separate adapter admission, risk-limit changes, and allocation execution across roles. Require adapter codehash/deployment-manifest allowlisting and protocol identity checks; stage adapter additions and cap increases with a delay so users can exit.

## [LENDACCESS-7] Unbounded and duplicate adapter registration can gas-brick all share conversions on Base
**Severity**: Medium
**Category**: evm-audit-defi-lending / evm-audit-access-control / evm-audit-dos
**Location**: `NavyVaultSRCLA.registerAdapter()`
**Description**: There is no cap on `_activeAdapters`, and the duplicate guard permits re-registering an `Active` adapter because `Active` is enum value zero. Each call appends another element. `totalAssets()` iterates the full array on every deposit, mint, redeem preview, and share conversion; `synchronousLiquidity()` additionally performs an external call for every entry. A compromised or erroneous admin can cheaply fill this array on Base until normal user operations exceed the block gas limit. Duplicates also multiply-count the same strategy balance before the gas limit is reached.
**Proof of Concept**: Repeatedly call `registerAdapter(A, ...)` while A is Active. Every call succeeds and pushes A again. Gas for `totalAssets()` and ERC-4626 entry points grows linearly; gas for `synchronousLiquidity()` grows with an external `maxWithdrawable` call per duplicate. Once the loops exceed Base's transaction gas limit, deposits and any withdrawal limit calculation invoking them are permanently unavailable unless the admin removes entries one transaction at a time; `_removeAdapter` removes only the first matching duplicate.
**Recommendation**: Reject `registeredAdapters[adapter] == true`, enforce a small governance-set maximum adapter count, and maintain an enumerable set with uniqueness. Make removal purge all impossible legacy duplicates or add a bounded repair migration before deployment. Add gas-bound invariants at the maximum supported adapter count.

## [LENDACCESS-8] Unbounded risk parameters can disable allocation or authorize complete realized loss
**Severity**: Medium
**Category**: evm-audit-defi-lending / evm-audit-access-control / evm-audit-dos
**Location**: `NavyVaultSRCLA.registerAdapter()` and `NavyVaultSRCLA.setMinIdleBps()`
**Description**: `capBps`, `maxLossBps`, and `minIdleBps` are denominated in basis points but have no `<= 10_000` validation. An admin mistake or compromise can set `minIdleBps > 10_000`, making `_requiredIdle()` exceed NAV and every Deploy action revert; `capBps > 10_000` defeats strategy concentration limits; `maxLossBps >= 10_000` authorizes a divest that returns zero while recognizing the entire position as loss. Changes are immediate and `setMinIdleBps` emits no event. Conversely, a legitimately impaired position whose loss exceeds a low configured bound cannot use `emergencyExit`, because that function calls the same loss-limited `_divest` path.
**Proof of Concept**: Register an adapter with `maxLossBps = 65_535` and set `minIdleBps = 20_000`. All new deployments revert `InsufficientIdle`. After resetting idle to zero, an adapter withdrawal of 0 against `amount` passes because `allowedLoss = amount * 65_535 / 10_000 > amount`, so the vault records a total loss without rejecting it. With an ordinary 100-bps limit and an actually impaired adapter returning 90%, `emergencyExit` instead reverts `AdapterLossExceeded`, preventing the named emergency operation.
**Recommendation**: Require all BPS inputs `<= 10_000`, define tighter governance maxima for loss and concentration, emit configuration-change events, and timelock increases. Give emergency exit an explicit admin-accepted `minOut`/maximum aggregate loss parameter or a staged impairment process rather than silently reusing the ordinary per-action bound.

## [LENDACCESS-9] NavyPayments owner can front-run a signed invoice and redirect the merchant proceeds
**Severity**: Medium
**Category**: evm-audit-defi-lending / evm-audit-access-control / evm-audit-dos
**Location**: `NavyPayments.setMerchantPayout()`
**Description**: A payer's EIP-3009 authorization binds payer, NavyPayments as receiver, amount, validity, and the merchant/invoice-derived nonce, but it does not bind the merchant's resolved payout address or current fee/treasury configuration. The sole owner can change payout, fee, and treasury instantly with no timelock. After seeing a relayed invoice transaction or obtaining its submitted authorization, a compromised owner can front-run `setMerchantPayout` and redirect `amount - fee` to an attacker while the original signature remains valid.
**Proof of Concept**: (1) A user signs an authorization for merchant M and invoice I. (2) Before the relayer's `payInvoice` is mined, the owner calls `setMerchantPayout(M, attacker)`. (3) The signed nonce and amount still validate because payout is not an EIP-3009 field. (4) `payInvoice` loads the updated Merchant struct and transfers the merchant portion to `attacker`. The owner can similarly raise the fee to 10% and redirect treasury immediately.
**Recommendation**: Put payment configuration behind a multisig/timelock with an activation delay. For invoices already issued, snapshot payout, fee, and treasury or bind a configuration/version hash into the durable invoice/authorization nonce and reject execution under a different version. Provide users/relayers a minimum notice window and cancellation path for pending authorizations.

## [LENDACCESS-10] Aave APR is scaled as if the already-annualized liquidity rate were per-second
**Severity**: Medium
**Category**: evm-audit-defi-lending / evm-audit-access-control / evm-audit-dos
**Location**: `AaveV3Adapter.supplyRatePerYear()`
**Description**: Aave `ReserveData.currentLiquidityRate` is an annualized supply rate expressed in RAY (1e27), not a per-second rate. The adapter multiplies it by `365 days` and divides by `1e27`, returning neither the documented 1e18 APR nor a valid annual rate. Any allocator comparing this result to Compound and Moonwell rates will systematically treat Aave as approximately 31.5 billion times less attractive than it is, invalidating lending allocation decisions.
**Proof of Concept**: For a 5% Aave liquidity rate, `currentLiquidityRate = 5e25`. The documented 1e18 result is `5e16`. The adapter returns `5e25 * 31_536_000 / 1e27 = 1_576_800`. Compound and Moonwell paths return per-second rates multiplied into 1e18 annual scale, so the values are not comparable.
**Recommendation**: Convert Aave's annual RAY directly to WAD: `return uint256(reserveData.currentLiquidityRate) / 1e9;`. Add fork assertions against Aave's official data provider/UI rate within a narrow tolerance and verify all adapters expose the same unit and compounding convention.

## Historical coverage / no-findings (2026-08-12 baseline)

- Lending and liquidation families: the repository supplies only to external lending markets and implements no borrowing, collateralization, liquidation, auction, repayment, insurance fund, or loan rollover. All checklist items specific to those absent state machines are not applicable. Aave siloed borrowing, eMode, isolation debt ceilings, cETH, and liquidation incentives are also inapplicable because the adapter supplies only canonical Base USDC and never borrows.
- Aave/Compound/Moonwell conformance: checked Base addresses/manifests, supply/withdraw selectors, return conventions, interest units, position valuation, cash-limited withdrawals, pause behavior, protocol identity, and reward claims. Compound III's `supply`, `withdrawTo`, `balanceOf`, utilization/rate surface, and base-liquidity bound are interface-compatible in isolation. Cross-vault adapter ABI drift is separately documented by the general audit; Moonwell-specific breakage is LENDACCESS-1 and Aave issues are LENDACCESS-4/LENDACCESS-10.
- Protocol pause/deprecation: adapter calls atomically revert, so no partial state survives; however try/catch only masks revert reasons and does not provide a fallback. Users are not liquidated during pauses. False liquidity reporting is LENDACCESS-4. No automatic migration from deprecated markets exists; governance must disable/impaired-state and divest when liquidity permits.
- Roles and privileged transitions: enumerated every owner, default-admin, admin, allocator, relayer, and vault-only mutation. User ERC-4626 receiver/owner parameters retain standard ERC-20 allowance checks. No public privilege escalation, initializer takeover, proxy upgrade, or arbitrary admin recipient in `emergencyExit` was found. Centralized key powers and inaccessible executor governance are reported above. The repo already lists multisig/timelock as a mainnet gate, but runtime code does not enforce it.
- Plan authorization/replay: completed and cancelled plans consume IDs in the current tree; proof execution now enforces sequential indices. No unprivileged replay was found. Zero plan IDs create unusable rather than privileged plans. Ignored policy/configuration commitments and the bypass path are LENDACCESS-3.
- Admin bounds and adapter lifecycle: reviewed state enum transitions, removal, empty checks, caps, loss limits, idle reserve, reward executor/routes, emergency exit, and configuration digests. Confirmed bounds/emergency mismatch is LENDACCESS-8. Adapter removal is based on cached assets and can require operational resynchronization, but re-registration from Removed permits admin recovery, so no separate permanent-loss finding was asserted.
- DoS/gas griefing: no fixed-gas low-level call, ETH push, user-controlled batch transfer, liquidation timing window, paymaster, or free public array-growth path exists. Adapter/reward calls use Solidity ABI decoding against admin-approved contracts; no unprivileged returndata-bomb target was confirmed. The privileged unbounded adapter loop is LENDACCESS-7. Merkle proofs and plan calldata are transaction-gas bounded and allocator-paid.
- Adapter read failures: `_syncStrategyAssets` preserves cached accounting on a failed read and `synchronousLiquidity` treats a failed liquidity read as fully liquid. The latter is reported in LENDACCESS-4. Cached accounting means accrued lending yield is recognized only on explicit sync/harvest, but because current first-party deploy/harvest paths are already nonfunctional, no additional standalone exploit was asserted without cross-fix assumptions.
- Deployment/config review: no first-party script deploys the Base adapter/executor system or establishes its roles. `base-strategies.json` lists an outdated/noncanonical Moonwell `unitroller`, while tests use the Comptroller implementation rather than the official Unitroller proxy; `base-reward-routes.json` also contains placeholder pools/feeds and reward token addresses inconsistent with source constants. These manifests are not consumed by any current script, so they are production blockers/configuration debt rather than independently reachable on-chain exploits.
- Verification: source-only `forge build --skip test` succeeds. The full build remains blocked by two stale RewardExecutor Route fixtures, and unfiltered Base fork execution was unavailable because `BASE_RPC_URL` was absent. The Moonwell selector, error-code, exchange-rate, Comptroller, and pause conclusions were cross-checked against Moonwell's official `moonwell-contracts-v2` interfaces and chain 8453 registry rather than inferred from skipped tests.
