## [GENERAL-1] The purported virtual offset disappears after the first deposit, leaving the vault open to a first-depositor inflation theft
**Severity**: Critical
**Category**: evm-audit-general
**Location**: `VaultMath.convertToShares()`
**Description**: `VaultMath` substitutes `VIRTUAL_ASSETS` and `VIRTUAL_SHARES` only when the corresponding real total is zero. Once one share exists, conversions use the unprotected `totalAssets / totalSupply` ratio. Because `NavyVaultSRCLA.totalAssets()` includes unsolicited asset transfers, a first depositor can donate assets, force a victim's deposit to round to zero shares, and redeem the victim's assets. The comments at `VaultMath.sol:9,17-22,29` claim OpenZeppelin-style inflation protection, but the implementation is not the additive virtual-assets/virtual-shares formula used for that protection. `ERC4626.deposit()` does not reject a zero-share result.
**Proof of Concept**: Starting from an empty vault, (1) the attacker deposits 1 USDC base unit and receives 1 share; (2) the attacker transfers 1,000,000 base units directly to the vault; (3) a victim deposits 1,000,000 base units; `convertToShares` returns `floor(1,000,000 * 1 / 1,000,001) = 0`, yet inherited `_deposit` transfers the victim's USDC and mints zero shares; (4) total assets are now 2,000,001 and total supply is 1, so the attacker redeems the sole share for all 2,000,001 base units. No privileged role or unusual token behavior is required.
**Recommendation**: Remove the custom conversion library and inherit OpenZeppelin 5.1's additive virtual accounting, optionally overriding `_decimalsOffset()` to a non-zero offset. If custom math is retained, apply virtual values additively on every conversion, honor the requested rounding direction, and reject deposits/mints that produce zero shares, e.g. `assets.mulDiv(totalSupply + VIRTUAL_SHARES, totalAssets + VIRTUAL_ASSETS, rounding)`.

## [GENERAL-2] The vault and every first-party adapter use incompatible runtime ABIs, permanently disabling deploy and divest actions
**Severity**: High
**Category**: evm-audit-general
**Location**: `NavyVaultSRCLA._deploy()` and `NavyVaultSRCLA._divest()`
**Description**: The vault's private `IStrategyAdapterVault` expects `deposit(uint256) returns (uint256)` and `withdraw(uint256) returns (uint256)`. All three first-party adapters implement `deposit(uint256)` with no return value and `withdraw(uint256,address)` with no return value through the different `IYieldAdapter` interface. Registration succeeds because `asset()`, `vault()`, and the read methods happen to match, hiding the incompatibility until value-moving execution. A deploy call reaches the adapter but then ABI-decodes empty returndata as `uint256` and reverts; a divest call uses selector `0x2e1a7d4d`, while adapters expose `withdraw(uint256,address)` selector `0x00f714ce`, so it reverts before withdrawal. Consequently all first-party strategy allocation, plan divestment, and emergency exit paths are permanently unavailable in the deployed bytecode.
**Proof of Concept**: (1) Deploy `NavyVaultSRCLA` and any of `AaveV3Adapter`, `CompoundAdapter`, or `MoonwellAdapter` with that vault address. (2) `registerAdapter` succeeds because its interface probes succeed. (3) Deposit idle USDC and execute a `Deploy` plan action. The vault transfers USDC and calls selector `deposit(uint256)` expecting 32 return bytes; the adapter returns none, Solidity ABI decoding reverts, and the entire transaction rolls back. (4) Any `Divest` or `EmergencyExit` action calls the nonexistent `withdraw(uint256)` selector and reverts. The repository's adapter fork tests do not reveal this because they call adapters directly with their own ABI, while vault tests use mocks implementing the vault's incompatible ABI.
**Recommendation**: Define one canonical adapter interface in one file and make both vault and adapters implement it. For the existing adapter custody design, a consistent surface could be `deposit(uint256) returns (uint256 credited)` and `withdraw(uint256) returns (uint256 returned)`, always returning funds to immutable `vault`; alternatively change the vault to the existing `withdraw(uint256,address)` ABI and measure balance deltas without decoding a nonexistent return. Add a test that registers each real adapter implementation in the real vault and executes deploy/divest end to end.

## [GENERAL-3] Re-registering an active adapter duplicates its assets in vault accounting
**Severity**: Medium
**Category**: evm-audit-general
**Location**: `NavyVaultSRCLA.registerAdapter()`
**Description**: The duplicate guard tests the adapter's enum state instead of `registeredAdapters`. `AdapterState.Active` is enum value zero, so an already registered active adapter satisfies the same state condition as an uninitialized mapping entry and may be registered repeatedly. Each call appends the address to `_activeAdapters`; `totalAssets()` and `synchronousLiquidity()` then iterate every duplicate and add the same `strategyAssets[adapter]` multiple times. This inflates share price, adapter caps, and advertised withdrawal liquidity and can make early redeemers take value from later users. The precondition is an admin transaction, so this is owner-only incorrect accounting rather than an unprivileged exploit.
**Proof of Concept**: (1) Register adapter A and establish `strategyAssets[A] = 100e6`. (2) While A is `Active`, call `registerAdapter(A, ...)` again. The condition at lines 278-280 does not revert because `AdapterState.Active == AdapterState(0)`. (3) `_activeAdapters` now contains `[A, A]`, and `totalAssets()` adds `strategyAssets[A]` twice, reporting 200e6 of strategy value for one 100e6 position. Repeating registration multiplies the overstatement and also grows the loops used by user-facing conversion functions.
**Recommendation**: Make `registeredAdapters` the sole duplicate guard: `if (registeredAdapters[adapter]) revert AdapterAlreadyRegistered();`. On removal, set the flag consistently and decide explicitly whether re-registration is supported. Add an invariant that every active-adapter address is unique and that the sum counted by `totalAssets()` contains each registered position once.

## [GENERAL-4] Paused `mint()` reports success without transferring assets or minting shares
**Severity**: Medium
**Category**: evm-audit-general
**Location**: `NavyVaultSRCLA.mint()`
**Description**: When paused, `mint()` calculates and returns an asset quote but never calls `_deposit`, transfers assets, or mints shares. A transaction therefore succeeds while performing none of the ERC-4626 operation its selector promises. This also contradicts `maxMint()`, which returns zero while paused, and the master SRCLA plan, which says pause must block deposits and mints. Integrators that treat a successful receipt/return value as issuance can record a nonexistent position. The existing test asserts only that the returned number is positive, so it codifies the false success without checking balances or supply.
**Proof of Concept**: (1) Pause the vault. (2) A user approves assets and calls `mint(500e6, user)`. (3) The call returns `_convertToAssets(500e6, Ceil)` successfully. (4) The user's USDC balance, allowance, vault asset balance, user share balance, and total supply are all unchanged. Thus the ABI-level operation says it succeeded while no mint occurred.
**Recommendation**: Match `maxMint()` and the documented emergency semantics by reverting while paused: `if (paused) revert DepositPaused(); return super.mint(shares, receiver);`. Update the test to expect a revert and assert no state changes. If paused issuance is genuinely desired, call `super.mint` and make `maxMint` consistent; do not return a quote from a mutating entry point.

## [GENERAL-5] The Base production deployment workflow is absent and the available vault script can deploy the wrong chain or asset
**Severity**: Medium
**Category**: evm-audit-general
**Location**: `script/DeployNavyVaultSRCLA.s.sol:10-28`
**Description**: Repository documentation describes a Base-only immutable core, claims it accepts only chain ID 8453 and Circle Base USDC, and instructs operators to run `DeployBaseVault.s.sol` and `AdminBaseVault.s.sol`; neither script exists. The only vault script is explicitly Sepolia-oriented, reads `SEPOLIA_USDC_ADDRESS`, and checks only that the supplied token reports six decimals. Neither the script nor the vault constructor checks `block.chainid`, the canonical Base USDC address, or even `address.code.length`. It also does not grant an allocator or deploy/register adapters and the reward executor. This is a concrete deployment/configuration mismatch: the documented production command cannot run, while the available command can successfully create a seemingly valid vault around any six-decimal token on any chain.
**Proof of Concept**: (1) Run the documented README command targeting `script/DeployBaseVault.s.sol:DeployBaseVault`; Foundry cannot find the file. (2) Instead run `DeployNavyVaultSRCLA` on any EVM chain with `SEPOLIA_USDC_ADDRESS` set to an attacker-controlled token whose `decimals()` returns 6. (3) Deployment succeeds and grants admin to the broadcaster, despite violating the documented Base/Circle-USDC invariant. (4) No allocator has been granted and no production dependencies are configured, so plan execution is unavailable until additional undocumented privileged transactions occur.
**Recommendation**: Supply and test the documented Base deployment/admin scripts. Before broadcast, assert `block.chainid == 8453`, the exact canonical Base USDC address, nonzero code at every dependency, and live protocol identity checks. Deploy or connect the executor/adapters, register them, grant a distinct allocator, and assert the complete post-deployment configuration in-script. Remove the obsolete Sepolia naming/instructions or clearly isolate them as a separate legacy deployment.

## [GENERAL-6] The complete Foundry build and test gate does not compile after the reward route interface change
**Severity**: Low
**Category**: evm-audit-general
**Location**: `test/reward/RewardExecutor.t.sol:722`
**Description**: `IRewardExecutor.Route` now contains ten fields after adding `feeTier`, but two current tests still construct the struct with nine. `forge build` compiles tests by default and fails at lines 722 and 765 with Solidity error 9755. Production sources compile only when tests are skipped, so the repository cannot run its stated build/test release gate and the new interface behavior is not fully regression-tested.
**Proof of Concept**: Run `forge build` in `contract/`. Solc 0.8.24 exits nonzero with `Wrong argument count for struct constructor: 9 arguments given but expected 10` at `RewardExecutor.t.sol:722` and `:765`. Running `forge build --skip test` succeeds, demonstrating that this is current interface/test drift rather than a toolchain installation failure. Running `forge test --skip RewardExecutor.t.sol` passes 219 tests with one RPC-gated skip, but necessarily omits the affected executor suite.
**Recommendation**: Add the intended `feeTier` to both remaining route fixtures and run the unfiltered `forge build` and `forge test` gates. Add CI that compiles the entire repository after every public struct/interface change; do not use `--skip test` as the release build.

## [GENERAL-7] Deployment fee narrowing can silently bypass the intended configuration bound
**Severity**: Low
**Category**: evm-audit-general
**Location**: `script/Deploy.s.sol:15`
**Description**: The deployment script casts an unrestricted environment `uint256` to `uint16` before passing it to `NavyPayments`. Solidity narrowing casts truncate instead of reverting, so the constructor's `MAX_FEE_BPS` check sees the truncated value rather than the operator-supplied value. A mistyped production value can silently deploy a materially different fee configuration; for example 65,536 becomes zero and 65,636 becomes 100.
**Proof of Concept**: Set `NAVY_FEE_BPS=65536` and run the deployment script. `uint16(vm.envUint("NAVY_FEE_BPS"))` evaluates to zero, the constructor's `feeBps > 1000` guard passes, and the deployed contract charges 0% despite the supplied configuration. This is not an unprivileged exploit, but it is a reachable deployment failure caused by unchecked downcasting.
**Recommendation**: Read into `uint256 rawFeeBps`, validate `rawFeeBps <= NavyPayments.MAX_FEE_BPS()` (and `<= type(uint16).max`) before casting, then assert the deployed `feeBps()` equals the requested value.
