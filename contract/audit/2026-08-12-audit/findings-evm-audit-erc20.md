The current working tree was reviewed against the Weird ERC-20 checklist, with Circle native USDC on Base/Sepolia treated as the deliberately fixed accounting asset. Severity follows the repository's master definitions: Critical means direct unprivileged theft or permanent loss; High means realistic loss/freeze, a privileged-but-plausible loss trigger, or pool-wide liveness failure; Medium means conditional loss, silent accounting corruption, or a meaningful safety gap; Low means limited/unlikely impact; Info means documentation or hygiene only.

## [ERC20-1] Ignoring ERC-4626 rounding modes enables zero-share withdrawals and overpaying redemptions
**Severity**: Critical
**Category**: evm-audit-erc20
**Location**: `NavyVaultSRCLA._convertToShares()` / `NavyVaultSRCLA._convertToAssets()` (`src/NavyVaultSRCLA.sol:691-712`), `VaultMath.convertToShares()` / `VaultMath.convertToAssets()` (`src/libraries/VaultMath.sol:31-72`)
**Description**: Both overrides discard the `Math.Rounding` argument. `_convertToShares` always floors, although ERC-4626 `previewWithdraw` must round shares up; `_convertToAssets` always rounds up, although `previewRedeem`, `convertToAssets`, and `maxWithdraw` must round assets down. Once `totalAssets() > totalSupply()` (the normal state after yield or a donation), a sufficiently small `withdraw` computes zero shares, burns nothing, and still transfers USDC. Repetition extracts pooled yield while the attacker retains all shares. Separately, splitting shares across repeated `redeem` calls collects the upward rounding remainder on every call and overpays early redeemers at later holders' expense. This is reachable by any shareholder and needs no privileged role. Circle USDC supports one-base-unit transfers, so six decimals do not prevent the exploit.
**Proof of Concept**: Start with `totalSupply = 100` and `totalAssets = 110`, with an attacker owning one share. `maxWithdraw(attacker)` is incorrectly `ceil(1 * 110 / 100) = 2`, so `withdraw(1, attacker, attacker)` passes. `previewWithdraw(1)` incorrectly floors `1 * 100 / 110` to zero; `_withdraw` burns zero shares and transfers one USDC base unit. Repeating while the price is above one drains the ten units of yield without reducing the attacker's one-share balance. The existing tests do not exercise fractional exchange rates for `previewWithdraw`/`previewRedeem`.
**Recommendation**: Preserve the requested rounding direction and use a full-precision `Math.mulDiv(..., rounding)` implementation (preferably OpenZeppelin's ERC-4626 conversion logic with a correctly scaled virtual offset). Add invariants that any nonzero successful withdrawal burns nonzero shares, `previewWithdraw` rounds up, `previewRedeem` rounds down, and splitting a redemption cannot increase aggregate assets received.

## [ERC20-2] The vault and every first-party adapter use incompatible deposit/withdraw ABIs
**Severity**: High
**Category**: evm-audit-erc20
**Location**: `IStrategyAdapterVault` / `_deploy()` / `_divest()` (`src/NavyVaultSRCLA.sol:17-27,564-614`), adapter `deposit()` / `withdraw()` implementations
**Description**: The vault calls `deposit(uint256) returns (uint256)` and `withdraw(uint256) returns (uint256)`. AaveV3Adapter, CompoundAdapter, and MoonwellAdapter implement `deposit(uint256)` with no return data and `withdraw(uint256,address)` with no return data. Aave/Compound deposits can execute their protocol call, but the vault then fails decoding the empty return value; transaction atomicity rolls the preceding USDC transfer and protocol supply back. Divest calls use a selector none of the adapters exposes and revert immediately. Consequently all first-party strategy deployment/divestment and emergency exits are unusable. Any position independently seeded into an adapter is stuck behind `onlyVault`, because the vault cannot invoke its withdrawal entrypoint.
**Proof of Concept**: Registering succeeds because all adapters implement `vault()`, `asset()`, and `totalAssets()`. A Deploy plan then transfers USDC to the adapter and calls selector `deposit(uint256)` expecting 32 return bytes; each implementation returns zero bytes, causing ABI decode failure and reverting the whole action. A Divest plan calls selector `withdraw(uint256)`, while each adapter only exposes `withdraw(uint256,address)`, so the call reaches no function and reverts. Moonwell remains broken even after only this mismatch is fixed: it attempts a second `safeTransferFrom(vault, adapter, amount)` after the vault already transferred the amount, and its `mint(address,uint256)` / `redeemUnderlying(address,uint256)` declarations do not match Base Moonwell's canonical `mint(uint256)` / `redeemUnderlying(uint256)` entrypoints.
**Recommendation**: Delete the duplicate inline and legacy interfaces and make the vault and all adapters compile against one `IStrategyAdapter`. Implement `deposit(uint256) returns (uint256 credited)` and `withdraw(uint256) returns (uint256 returned)` everywhere, hardcode withdrawals to the vault, and derive both return values from before/after USDC or protocol-position balance deltas. For Moonwell, use the canonical one-argument methods, approve mUSDC to pull the adapter's already-received USDC, and reject every nonzero numeric error code. Add real-adapter integration tests through the vault, not ABI-compatible mocks only.

## [ERC20-3] `maxWithdraw` includes adapter liquidity that withdrawals never retrieve
**Severity**: High
**Category**: evm-audit-erc20
**Location**: `maxWithdraw()` / `maxRedeem()` / `synchronousLiquidity()` (`src/NavyVaultSRCLA.sol:237-245,665-684`)
**Description**: `synchronousLiquidity()` adds the reported withdrawable value of active/disabled adapters, and `maxWithdraw`/`maxRedeem` advertise that value to users. The vault does not override ERC-4626 `_withdraw`, however, so an actual `withdraw` or `redeem` only burns shares and transfers the vault's current idle USDC; it never calls `_divest` or otherwise sources adapter liquidity. Once capital is allocated beyond the idle buffer, calls that are explicitly reported as available revert in `SafeERC20.safeTransfer`. Pausing also forces `maxRedeem` to zero despite the design requirement that redemptions remain available during emergencies. The adapter ABI failure in ERC20-2 currently prevents ordinary allocation, but any seeded adapter position reaches this failure immediately, and fixing ERC20-2 alone exposes it for every normal allocation.
**Proof of Concept**: With 50 USDC idle, 950 USDC in an adapter, and the adapter reporting 950 withdrawable, `synchronousLiquidity()` and `maxWithdraw` can report 1,000 USDC for the sole holder. Calling `withdraw(1_000e6, ...)` burns according to the preview and then inherited ERC-4626 `_withdraw` attempts a direct 1,000-USDC transfer from a 50-USDC balance; Circle USDC reverts for insufficient balance. No adapter withdrawal is attempted.
**Recommendation**: Override the withdrawal workflow to ensure sufficient idle assets before burning/transferring, divesting in a deterministic order with fixed recipient `address(this)` and validating the actual USDC balance delta and loss bound. Alternatively, advertise only idle USDC in `maxWithdraw`/`maxRedeem`. Keep both withdraw and redeem available while the vault-level deposit pause is active.

## [ERC20-4] Harvest output is trusted and then double-counted in vault NAV
**Severity**: High
**Category**: evm-audit-erc20
**Location**: `_harvestCore()` / `totalAssets()` (`src/NavyVaultSRCLA.sol:210-225,368-420`), `RewardExecutor.swap()` (`src/reward/RewardExecutor.sol:168-235`)
**Description**: `RewardExecutor.swap` transfers its output token to the vault and returns `amountOut`. `_harvestCore` trusts that return value without measuring the vault's native-USDC balance delta, adds it to `recognizedRewards`, and `totalAssets()` also counts the same USDC through `IERC20(asset()).balanceOf(address(this))`. A 10-USDC successful harvest therefore raises reported NAV by 20 USDC. A buggy/misconfigured executor can also return an arbitrary number or transfer a non-USDC route output, because the vault never verifies the received asset. Inflated NAV under-mints later depositors and lets early redeemers withdraw more than their pro-rata share, leaving later holders with reverting or underfunded claims. Current first-party adapters report zero claimable rewards and the bundled executor cannot be configured as deployed (ERC20-5), so exploitation is presently gated by the privileged-but-plausible act of enabling a functional reward path or registering a reward-bearing adapter; it becomes unprivileged after that normal production step.
**Proof of Concept**: Before harvest, let actual and reported assets both equal 100 USDC. A compliant executor swaps rewards and transfers 10 USDC to the vault, so idle balance becomes 110. The vault also executes `recognizedRewards += 10`, making `totalAssets()` return 120 despite only 110 existing. With two equal holders, the first 50-share redemption is priced at 60 USDC instead of the fair 55, transferring 5 USDC of the second holder's claim to the first.
**Recommendation**: Define whether `recognizedRewards` represents unreceived marked-to-market rewards or received USDC; never count received USDC twice. Around each swap, measure `asset().balanceOf(address(this))` before and after and use only the delta as realized output. Require the executor route output to equal the immutable vault asset. Clear/decrease any prior recognition when rewards become realized, and add the conservation invariant `totalAssets <= realizable idle + strategy value + separately valued unreceived rewards - losses`.

## [ERC20-5] The shipped reward path cannot claim tokens or configure any swap route
**Severity**: Medium
**Category**: evm-audit-erc20
**Location**: `_harvestCore()` (`src/NavyVaultSRCLA.sol:368-419`), `RewardExecutor.constructor()` / `approveRoute()` (`src/reward/RewardExecutor.sol:71-129`), adapter `claimableReward()` implementations
**Description**: `_harvestCore` reads `claimableReward` but never calls a claim function or measures reward tokens received. It instead approves the executor from the vault and asks it to pull `claimable`, although claimable tokens reside in/are owed to the adapter. All three first-party adapters hardcode `claimableReward` to zero and expose no claim entrypoint, making harvest a no-op. Independently, RewardExecutor grants both admin roles only to the immutable vault address, but NavyVaultSRCLA exposes no forwarding function that calls `approveRoute` or `revokeRoute`; after deploying the executor with the actual vault address, no externally controlled account can add a route, and every nonzero swap reverts `RouteNotFound`. Rewards can therefore accrue without a working route from the protocol to USDC.
**Proof of Concept**: Deploy `RewardExecutor(address(vault), router)`. The deployer/admin EOA has no role, so its `approveRoute` call reverts. The vault contract owns the role but has no function that makes the call. Meanwhile `AaveV3Adapter.claimableReward(COMP)`, `CompoundAdapter.claimableReward(COMP)`, and `MoonwellAdapter.claimableReward(WELL)` always return zero. `vault.harvest(...)` thus returns zero; if one method is changed to report a positive claimable amount without also transferring it to the vault, `safeTransferFrom(vault, executor, claimable)` reverts for insufficient vault reward-token balance.
**Recommendation**: Implement a single, tested claim flow on `IStrategyAdapter` that transfers the actual claimed amount to the vault (or lets the executor pull an exact approved amount directly from the adapter), return/measure actual balance deltas, and revoke/reset exact allowances. Give route administration to a timelocked admin/multisig or add narrow vault forwarding methods. Verify end to end on a Base fork: claim protocol incentives, swap an approved route, receive only native USDC in the vault, and reconcile NAV exactly once.

## [ERC20-6] Self-payout and unsolicited transfers can permanently strand USDC in NavyPayments
**Severity**: Low
**Category**: evm-audit-erc20
**Location**: `registerMerchant()` / `setMerchantPayout()` / `payInvoice()` (`src/NavyPayments.sol:85-103,105-136`)
**Description**: Merchant payout validation rejects only the zero address. If the owner configures `address(this)` as the payout, `payInvoice` transfers the merchant portion from NavyPayments back to itself, records the invoice as paid, and leaves that portion permanently resident. Users can also send USDC directly to the contract. There is no recovery path for either balance, even though the normal invariant after a payment is a zero USDC balance. This does not let an attacker take other users' funds and requires misconfiguration or accidental transfer, so impact is Low.
**Proof of Concept**: Register a merchant with `payout = address(NavyPayments)` and execute a 100-USDC invoice at a 1% fee. The contract receives 100, transfers 99 to itself (net balance unchanged), transfers 1 to treasury, emits `InvoicePaid`, and retains 99 USDC. No function can move the retained balance afterward.
**Recommendation**: Reject payout addresses equal to the payment contract or USDC contract. Consider a tightly scoped owner recovery function for unsolicited excess balances, with events and an explicit accounting invariant showing that NavyPayments never intentionally retains payment principal.

## Historical coverage and no-findings (2026-08-12 baseline)

- Reviewed all first-party Solidity under `contract/src`, with token-flow emphasis on NavyPayments, NavyVaultSRCLA, AaveV3Adapter, CompoundAdapter, MoonwellAdapter, and RewardExecutor. Traced every `transfer`, `transferFrom`, SafeERC20 call, approval, balance read, EIP-3009 receive, adapter deposit/divest, reward swap, and ERC-4626 share action.
- EIP-3009 binding in `payInvoice` is sound for Circle's `receiveWithAuthorization`: the signed fields bind payer, this contract as recipient, value, validity window, and the fixed-width `keccak256(merchantId, invoiceId)` nonce. Setting `invoicePaid` before the call is safe because any later USDC/payout/treasury revert rolls the entire transaction back, including Circle authorization state and `invoicePaid`.
- Circle native USDC's current implementation returns `true` or reverts for `transfer`/`approve`, permits zero-value transfers, permits nonzero-to-nonzero allowance updates, has six decimals on Base/Sepolia, and is not fee-on-transfer or rebasing. Accordingly, NavyPayments' unchecked transfer returns and Aave/Compound's raw approvals are accepted USDC-specific assumptions rather than generic-token findings. SafeERC20 is still preferable for defense against proxy upgrades and clearer intent.
- Zero-value handling in NavyPayments is safe: invoice principal is bounded by `MIN_INVOICE_AMOUNT`, merchant output is nonzero under the fee ceiling, and the zero fee leg is skipped. Standard vault zero transfers are accepted by native USDC.
- Circle pause, denylist, privileged mint/burn, and proxy-upgrade powers are accepted common-mode dependencies explicitly called out by the design. A pause or denylisting the vault/payment contract makes affected transfers revert; payment state remains retryable through transaction rollback, while pooled vault funds remain unavailable until Circle restores transferability. This operational freeze risk is not represented as protocol diversification.
- No arbitrary-token entrypoint, ERC-777 hook surface, native/ERC-20 dual representation, flash-mint pricing input, metadata decoding, DAI permit, phantom permit, or cross-chain decimal conversion was found in the scoped Solidity. The Base vault intentionally has no EIP-3009 or ERC-2612 user path; EIP-3009 exists only in NavyPayments.
