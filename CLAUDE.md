# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**SRCLA** — *Safe, Robust, Cost-Aware Lending Allocation for ERC-4626 Vaults* — the research codebase for the thesis on optimized ERC-20 allocation across decentralized lending protocols. It allocates a pooled USDC vault across Compound III, Aave V3 and Moonwell on **Base (EVM, chainId `8453`)**. **There is no testnet deployment** — local dev runs against an **Anvil fork of Base mainnet** on `:8545` (see *Running locally*).

**This repo is the algorithm only.** The Navy payment ecosystem that used to live here — the `NavyPayments.sol` gateway, the NestJS backend `be/`, the Next.js merchant/admin web `fe/` and the Expo wallet `expo-wallet/` — was **removed on 2026-09-13**. It survives only in git history (`git show deae8408:<path>`); some specs, plans and audit documents still mention it as historical context. Do not wire anything back to it. What remains is **two independent apps** (not a workspace — each has its own tooling):

| Dir | Stack | Role |
|---|---|---|
| `srcla/` | TypeScript + Fastify 4 + Prisma **5** (Postgres `:5433`) | The algorithm as a **long-running service** (`:3100`): snapshot collection, forecasting, allocation decisions, on-chain keeper execution — plus the registered evaluation harness |
| `contract/` | Foundry (Solidity 0.8.24) | `NavyVaultSRCLA.sol` (pooled ERC-4626), the `IStrategyAdapter` venues, `RewardAccountant`/`RewardExecutor`, deploy scripts, audit |

Report outputs live in `report/`: `SRCLA-REPORT.md`, its figures in `report/figures/` (`SRCLA-FIG*` as SVG, plus PNG from `pnpm figures:render --png`, and `image.png`, Moonwell's Base USDC market at 100% utilization) and the numbers the figures are drawn from in `report/chart/SRCLA-FIGURE-SWEEP-*.json`. `SRCLA-REPORT.json` and the gitignored run records `evaluation-heldout-*.json` stay at the repo root. Everything but `image.png` is generated by `srcla/scripts/run-phase4.ts`.

**Development is spec-driven.** Features are designed → planned → built via `docs/superpowers/specs/*-design.md` + `docs/superpowers/plans/*.md`; read the relevant one before changing a subsystem, since they hold the *why* and the locked decisions. **`docs/` is untracked (see the gotcha below), so the live specs/plans exist only on the local disk** — list them with `ls docs/superpowers/{specs,plans}`. The line runs: paper conformance (2026-09-07/08, phases 1–4 complete) → v0.7 movement rule and release readiness (2026-09-09) → P36 hurdle bound (2026-09-13, never committed). `plans/2026-09-07-srcla-phase1-outcome.md` holds the operator runbook. Obsolete designs were deleted (commit `7127ce2`, and the app-specific ones on 2026-09-13) and exist only in git history — bound the search to before the untracking commit, which deletes every doc: `git log --diff-filter=D --name-only deae8408 -- docs/superpowers`, then `git show <commit>^:<path>`.

Other durable design docs: `docs/research/output/srcla-paper.md` (the algorithm), `docs/research/` (supporting research), `docs/PRODUCTION.md` (all local-only), `contract/DEPLOYMENTS.md`, `contract/script/POST_DEPLOY.md`, `contract/audit/`.

Run inside the relevant app dir.

```bash

pnpm dev                          # tsx watch src/index.ts — serves /v1/* on :3100 AND runs the scheduler
pnpm build && pnpm start          # tsc, then node dist/index.js
pnpm exec tsc --noEmit            # typecheck src/ — passes
pnpm typecheck:scripts            # typecheck scripts/ — currently FAILS on pre-existing errors in 8 scripts
pnpm lint                         # eslint src
pnpm test                         # jest test/unit + test/integration (NOT unit-only; integration needs Postgres)
pnpm test:unit | test:integration | test:eval        # narrower suites (test:all runs all three)
pnpm cli:health                   # health probe (also cli:collect / cli:evaluate / cli:regime)
pnpm collect                      # one-shot market snapshot
pnpm evaluation:run --era heldout-c [--tiers 10000,100000] [--out run.json]   # ONE registered era; phase4:run does both + the report
pnpm prisma:push                  # after schema.prisma changes — Prisma 5

# contract/  (Foundry; fork tests need BASE_RPC_URL — point it at the local Anvil fork)
forge build                       # compile; ABIs land in out/<Contract>.sol/<Contract>.json
forge test                        # unit + fuzz/invariant + Base-fork tests
forge script script/DeployNavyVaultSRCLA.s.sol --fork-url http://127.0.0.1:8545 --broadcast   # --slow against 7702-delegated accounts
```

**Running locally** — order matters, each step depends on the one above:

1. **Anvil fork of Base mainnet:** `anvil --fork-url https://mainnet.base.org --code-size-limit 100000` (`:8545`). This *is* the chain for local dev.
2. **Deploy + configure:** `cd contract && forge script script/DeployNavyVaultSRCLA.s.sol --fork-url http://127.0.0.1:8545 --broadcast`, or `DeployAndFund.s.sol` for funded multi-tier vaults with the three adapters registered. Other entry points: `DeployBaseSystem.s.sol` (full Base package), `VerifyBaseSystem.s.sol` (read-only conformance check of a deployment), `RunBaseAcceptance.s.sol`, `WriteDeploymentManifest.s.sol`, `AnvilE2ETest.s.sol`, `ConfigureAnvil.s.sol` (tops up a vault — reads `VAULT_ADDRESS` from the env), `FundVaultAnvil.s.sol`. Deploy scripts apply the paper's on-chain guardrails via `script/VaultGuardrails.sol`; the required post-deploy step is in `script/POST_DEPLOY.md`. Older docs name deploy scripts that no longer exist (`Deploy.s.sol`, `DeployVaultAnvil.s.sol`, the deleted `NavyVaultSimple` stub's four scripts) — `ls contract/script` is the real set. Then **write the new addresses into `srcla/.env.anvil`** (and `srcla/.env`) — they change on every redeploy.
3. **Postgres 16:** `cd srcla && docker compose up -d` gives `srcla` on **:5433** (`DATABASE_URL=postgresql://user:password@localhost:5433/srcla`), then `pnpm prisma:push`.
4. `cd srcla && pnpm dev` — public API on `:3100`, operator listener on `127.0.0.1:3101`.

**Single test — srcla:** `NODE_OPTIONS='--experimental-vm-modules' pnpm exec jest --runInBand test/unit/evaluation/charts.spec.ts`. **Not** `pnpm test:unit <fragment>`: Jest ORs the fragment with the script's `test/unit`, so that runs the whole unit suite (~2 min). **Not** a raw `npx jest` either: without `NODE_OPTIONS=--experimental-vm-modules` five policy suites fail on `import.meta` (TS1343) — that is the invocation, not the code. **Contract:** `forge test --match-test`/`--match-contract`. Chain calls are NOT unit-testable — verify them on the fork: `source .env.anvil && pnpm phase1:check` runs one real decision cycle and attempts keeper execution of its plan; `pnpm anvil:test` deploys and runs the algorithm end-to-end; the forge fork suites cover the contracts.

## Architecture (the parts that span files)

**The vault (pooled ERC-4626).** **`NavyVaultSRCLA`** (`contract/src/NavyVaultSRCLA.sol`) is a pooled ERC-4626 over Circle USDC that mints `navUSDC` shares (ERC20Permit). **Deposits and redemptions are user-signed and user-paid** (paper §2.1): there is no relayer and no sponsored gas. The user approves USDC then calls `deposit`/`mint`, and redeems via `redeem`/`withdraw`. A constrained **ALLOCATOR** keeper rebalances the pool across owner-allowlisted **`IStrategyAdapter`** venues (`CompoundAdapter`, `AaveV3Adapter`, `MoonwellAdapter`) under **on-chain** `capBps`/`minIdleBps`/`maxLossBps` guards — the contract is the authoritative guardrail: the allocator can only move funds *between allowlisted adapters*, never to an EOA (verified in the audit). `submitPlan` checks those guards against the vault's own NAV. `RewardAccountant.syncForShareAction` runs on every `deposit`/`mint`, so a vault the accountant does not authorise reverts every deposit (`script/POST_DEPLOY.md`). Audit: `contract/audit/AUDIT-REPORT.md` + `contract/audit/2026-08-12-audit/findings-evm-audit-*.md`, release evidence in `contract/audit/RELEASE-EVIDENCE-2026-08-14.md`, post-audit changes in `contract/audit/2026-09-07-phase2-changes.md`.

**`srcla/` is a running service.** It is not an offline harness — `srcla/src/index.ts` boots a **Fastify** API (`srcla/src/http/{server,routes}.ts`; `HTTP_HOST`/`HTTP_PORT`, default `:3100`) *and* a **scheduler** (`srcla/src/runtime/scheduler.ts`: snapshot collection every `COLLECTOR_INTERVAL_MS`, decision cycles on the controller interval, weekly walk-forward calibration — 30d window / 7d held-out / 7d horizon), and it owns **on-chain keeper execution** via `KeeperExecutor` (`srcla/src/execution/keeper-executor.ts`). **Two listeners.** The public one (`HTTP_PORT`, default `:3100`) is **GET-only and enforced so**: an `onRoute` hook records every route and throws on any non-GET/HEAD/OPTIONS, so adding a POST there makes the service fail to boot (paper §10.2). It serves `health`, `markets[/:marketId]`, `decisions[/:hash]`, `plans`, `harvests`, `allocation`, `evaluations`, `regimes[/:marketId]`, `simulations/:marketId`, `manifests[/:id[/verification]]`, `enumeration/:cycleId`, `reserve`, `emergencies`, `policy`, `sync`. The three mutations — `POST /v1/{manifests,proposals/review,internal/trigger}` — live on a **loopback-only operator listener** (`OPERATOR_HTTP_PORT`, default `:3101`, bound to `127.0.0.1` as a code constant, not an env var). **The keeper key lives only in srcla, and nothing reachable from the public listener can send a vault transaction** — keep it that way.

**The decision pipeline** is `srcla/src/policy/decide.ts`, which runs the steps in `policy/steps/` in this order: `admit` → `safetyUnwind` (can short-circuit to an unwind plan) → `simulateCurves` → `forecastMarkets` (§7 lower bounds) → `optimize` (§8.2 enumeration) → `requiredReserve` (§8.1) → `applyBrakes` → `buildPlan`; the movement hurdles (`steps/hurdles.ts`) and cost terms (`steps/cost.ts`, §9.1) are applied within that chain. Around it, in `srcla/src/`: `collector/` (live snapshots through the deployed adapters; `archive/` for the backfill), `forecast/` (forecasters, calibration, grid sweep), `regime/`, `execution/` (plan builder, preflight, `KeeperExecutor`, reconciler), `evaluation/` (the registered evaluation, §11), `domain/` (shared types and digests), `chain/`, `db/`, `protocols/` (rate models), `cli/`. Every knob is an `SRCLA_*` env var in `srcla/src/config.ts`, mapped to its paper section.

**Off the live path — do not extend these thinking they run.** `admission/`, `decision/`, `reserve/` and `oracle/` are imported only by their own unit tests; `optimizer/` only by the quarantined policy (`evaluation/quarantined/`); `rewards/` and `policy/harvest.ts` (§9.2–§9.4) by nothing at all. The live admission and reserve are `policy/steps/admit.ts` and `policy/steps/reserve.ts`.

## Critical conventions & gotchas

- **Deployed addresses are NOT hardcoded here — read them from the env files.** Every local deploy is a fresh Anvil fork of Base, so vault/adapter addresses change constantly. Sources of truth: **`srcla/.env.anvil`** (`VAULT_ADDRESS` + `COMPOUND_/AAVE_/MOONWELL_STRATEGY_ADDRESS`, `REWARD_EXECUTOR_ADDRESS`, `REWARD_ACCOUNTANT_ADDRESS`) and **`contract/DEPLOYMENTS.md`** for the deployment package. ⚠️ Every address recorded before Phase 2 refers to superseded bytecode (banner at the top of `DEPLOYMENTS.md`).
- **Constants that *are* safe to hardcode (Base mainnet, and the fork inherits them).** Circle USDC `0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913`. Venues: Compound III Comet `0xb125E6687d4313864e53df431d5425969c15Eb2F` (its `baseToken()` is that USDC), Aave V3 Pool `0xA238Dd80C259a72e81d7e4664a9801593F98d1c5`, Moonwell mUSDC `0xEdc817A28E8B93B03976FBd4a3dDBc9f7D176c22`. Full table (Uniswap, Chainlink feeds, sequencer uptime) in `contract/DEPLOYMENTS.md`.
- **Compound Comet `withdraw` + public RPCs:** some public `eth_estimateGas` endpoints spuriously revert for Comet `withdraw`/`withdrawTo` even though `eth_call` + real execution succeed — pass an explicit `gasLimit` for the vault's adapter-withdraw / redemption txs, or use a real RPC (Alchemy/Infura). Comet also floors ~2 base units on supply: the vault has no absolute dust allowance, so its synchronous-loss guardrail (`contract/script/VaultGuardrails.sol`) must stay non-zero or dust reverts redemptions, and `CompoundAdapterForkTest` reads the credited balance rather than asserting an exact round-trip.
- **`forge script` against an EIP-7702-delegated account needs `--slow`** — some RPCs reject gapped nonces from delegated accounts.
- **SDK drift is real — verify before coding.** `srcla/` is on **Prisma 5 + Fastify 4 + ethers v6**; those have breaking changes vs later majors and vs training data, so consult the installed `node_modules` types before trusting a version-specific pattern.
- **Env:** `srcla` loads `srcla/.env` via `dotenv/config` in `src/config.ts` (validated by a zod schema — a missing/malformed var fails fast at boot); `srcla/.env.anvil` is sourced by hand for fork scripts. `contract/.env` feeds the forge scripts (see `contract/.env.example`). `deploy/` holds gitignored local deploy material (`base-wallets.env`, `README.private.md`) — never commit its contents.
- **`docs/` is in `.gitignore` and untracked (commit `18595bbf`, 2026-09-13).** Its specs, plans, research and the paper live only on the local disk; versions from before then are in git history (`git show deae8408:docs/<path>`). Consequences in a fresh clone: `srcla/test/unit/evaluation/paper-amendments.spec.ts` reads `../docs/research/output/srcla-paper.md` and **fails**, and `contract/README.md`'s link to `../docs/PRODUCTION.md` is dead. Do not link `docs/` from tracked files.
- **Production gates + accepted pre-production risks:** `docs/PRODUCTION.md` (local-only) — independent audit, owner → multisig/timelock, KMS/HSM key custody. New work: branch off `main`.

**SRCLA Paper & evaluation.** Algorithm spec: `docs/research/output/srcla-paper.md` — **v0.10**, carrying Amendment Records P1–P36 and three burned-window declarations; both are binding spec, not proposals. The registered evaluation has been RUN on both sealed eras and returns `FAIL` (published, not tuned away); §13 and Appendix F of the paper hold the results and the disclosures. Defines baselines B0–B5 (incl. B2u), ablations **H1–H7**, and two release gates (forecast calibration + policy outperformance). Evaluation report: `report/SRCLA-REPORT.md` (+ `SRCLA-REPORT.json` at the root). The registered evaluation is `pnpm phase4:run` (both eras + report) or `pnpm evaluation:run --era` (one era). **Two scripts look like evaluations and are not:** `srcla/scripts/run-live-evaluation.ts` is a hard-coded illustration (fixed market numbers; it never reads the fork), and `pnpm evaluation:full` (`run-evaluation-full.ts`) uses hard-coded rates and printed `Date.now()` as its "content hash" (`src/evaluation/kernel/provenance.ts`). `scripts/show-live-apys.ts` prints the venue APYs the fork is currently reporting.

> Point-in-time numbers (APYs, capital at work, gate results) are **not** kept here — they go stale on every run. Read them from `report/SRCLA-REPORT.md` / `SRCLA-REPORT.json` or re-run the evaluation.

### The dataset and the eras

Phase 4 backfilled **21,769 hourly origins from 2024-03-15** of Base mainnet venue
state (Compound III, Aave V3, Moonwell) with **zero gaps**, reading the protocols
directly at archive blocks — `pnpm backfill:history`, resumable, multi-endpoint.
Base archive state for all three venues reads back to the deployment floor (block
11,707,031, 2024-03-12).

`srcla/src/evaluation/eras.ts` is the registered split, and it is enforced in code
(`assertNotSealed` throws; `loadEra` is the only loader that takes an era):

| Era | Window | Days | Role |
|---|---|---|---|
| `calibration` | 2024-03-15 → 2025-05-31 | 443 | the ONLY data anything may be fit on |
| `burned-a` | 2025-06-01 → 2026-02-28 | 273 | former held-out A; burned while diagnosing v0.5. Reported by nothing |
| `heldout-c` | 2026-03-01 → 2026-05-25 | 86 | **sealed** — the era with statistical power |
| `burned` | 2026-05-26 → 2026-08-23 | 90 | §4.1 design data; in NEITHER era |
| `heldout-b` | 2026-08-24 → present | open | **sealed**, open-ended — temporal purity, low power |

**There is no `heldout-a`** — it was renamed `burned-a` when v0.5's diagnosis read
its aggregates. Read the windows from `eras.ts`, never from memory.

Two deviations stay disclosed in any report: §4.1's letter puts the burned window
inside calibration and here it is in neither (including it would place fitting data
*after* `heldout-c` and invert walk-forward order); and `heldout-c` *precedes* the
burned window, so it carries a design-knowledge caveat `heldout-b` does not.
**Both sealed eras are reported; neither alone is sufficient.**

⚠️ **`heldout-c` is DESIGN DATA as of v0.9.** The first registered run opened it,
returned `FAIL`, and its results then informed P29 and P31. Any further result
against it is a CONFIRMATORY RE-RUN, not a fresh test. `heldout-b` grows with the
live collector and is the only era that will carry no design knowledge.

**`phase4:run` is a LONG, SILENT job.** It prints an era header, then nothing for
hours while it replays 16 policies x 4 tiers x ~2,000 origins, then the gates. To
tell a working run from a hung one, check the worker's accumulated **CPU time**, not
stdout — and note `pgrep -f` matches its own shell and the `sh -c` wrapper, both of
which show 0% CPU, so it reports RUNNING for things that are dead:

```bash
ps -eo pid,etime,time,%cpu,args --sort=-%cpu | grep run-phase4 | head -2
```

**§11.1's fork replay needs a fork AND four per-tier vaults**, or it reports NOT
PRODUCED and the gate blocks. `submitPlan` verifies `capBps`/`minIdleBps`/reserve
against the VAULT'S OWN NAV, so every registered tier needs a vault deployed at that
scale carrying `harnessConfig`'s registered values (capBps 5000, maxLossBps 50,
minIdleBps 500) — `DeployAndFund.s.sol` does this. Then:

```bash
export SRCLA_FORK_REPLAY_RPC_URL=http://127.0.0.1:8545
export SRCLA_FORK_REPLAY_VAULT_ADDRESS=0x…       # fallback vault
export SRCLA_FORK_REPLAY_ALLOCATOR_KEY=0x…       # holds ALLOCATOR_ROLE
export SRCLA_FORK_REPLAY_ADAPTERS=compound-v3-usdc=0x…,aave-v3-usdc=0x…,moonwell-usdc=0x…
export SRCLA_FORK_REPLAY_TIER_VAULTS="10000000000=0xVault|compound-v3-usdc=0x…,…;…"

```

the single vault and carries the disclosed one-NAV caveat.

`pnpm digests:rewrite` repairs persisted `configDigest`s in place if the format
changes; it re-derives from columns already stored and fetches no blocks.

### Things that will bite you

- **The backfill CANNOT reuse `SnapshotCollector`.** That reads venue state through
  the deployed Navy adapters, which exist only on the Anvil fork and have no Base
  mainnet history. `src/collector/archive/calls.ts` reads Comet, the Aave Pool and
  the mToken directly — one multicall3 `aggregate3` per origin, 39 legs.
- **`configDigest` is `identity|parameters`** (`src/domain/config-digest.ts`).
  Identity is protocol + market contract and is what `CONFIG_DIGEST_MISMATCH` pins;
  parameters include the rate-model address and coefficients and are what starts a
  new regime. Conflating them makes every venue permanently inadmissible at its
  first governance rate change — the registered window holds 6 Compound, 14 Aave
  and 11 Moonwell parameter regimes. A pin registers a SET of identities.
- **IRM parameters are read from chain, not from `DEFAULT_*_CONFIG`.** Those
  placeholders assert an 80% kink and a 6.25% low slope; Compound's real values are
  **90%** and **~3.60%**. Compound's rate is computed per-second and annualized
  afterwards, reproducing `Comet.getSupplyRate` exactly.
- **`vm.prank`/`vm.startPrank` funding in a deploy script SILENTLY FAILS under
  `--broadcast`.** The cheat applies to the simulation pass only; the broadcast pass
  replays against the real chain where the prank never happened, so every transfer
  reverts with "transfer amount exceeds balance" AFTER the contracts are deployed.
  Fund the deployer out of band (`cast rpc anvil_impersonateAccount` on a whale, then
  `cast send`) and have the script `require` the balance instead.
- **`report/SRCLA-REPORT.md`, `SRCLA-REPORT.json`, `report/figures/SRCLA-FIG*` and `report/chart/SRCLA-FIGURE-SWEEP-*.json`
  are GENERATED** by `phase4:run` from `src/evaluation/report/` (`render-markdown.ts`, `charts.ts`); the retired
  untracked `srcla/quarantine/evaluation-v2/*.mjs` harness produced every earlier version. Hand-edits are erased
  on the next run — change the renderer, not the file. A renderer edit does NOT affect a run already in flight
  (Node has loaded the module), but a `charts.ts` edit needs no run at all: the figures are drawn from the
  persisted sweep, and `pnpm figures:render --png` redraws them from `report/chart/`. `phase4:run` writes SVGs
  only; the PNGs for Word/LaTeX come from `figures:render --png` (headless Chrome).
- **`test/unit/chain/chain.spec.ts` makes live RPC calls inside the unit suite** and
  fails intermittently on timeouts, especially under concurrent load. It passes on
  re-run. Treat a lone `chain.spec` failure as flake, not regression.
- **Gas and oracle inputs are MEASURED per origin** (`ChainCostSnapshot` +
  `src/evaluation/gas-series.ts`), not the five constants `harnessConfig` used to
  assert. The series refuses to extrapolate backwards and carries a digest, because
  the manifest's dataset hash covers snapshots and withdrawals only.
- **A registered artifact is FROZEN.** `prepareArtifact` returns it untouched;
  re-fitting it against a held-out era would train the policy on the data the run
  exists to test.
- **The movement hurdles read the RELATIVE bound (P36).**
  `srcla/src/policy/steps/hurdles.ts#annualLowerBound` must stay on P29's
  `rate·(1+q_rel)` form whenever the artifact carries
  `relativeResidualQuantileWadByMarket`; the additive form is only the fallback for an
  artifact without it (the live bootstrap one). Before P36 the hurdles kept the
  additive haircut after P29 moved the objective, which idled much of the 10M tier's
  capital. `disable.uncertainty` (H2, B3) removes the haircut in the hurdles too.
